Agente de Órdenes de Compra SAP

Un agente conversacional en TypeScript que lee el paquete de una solicitud de compra, valida los controles, construye la orden de compra y la crea en un SAP simulado, pidiendo confirmación humana cuando hay excepciones.

Autor Jose Sebastian Garzon ParraFecha Octubre 2026Stack TypeScript · Bun · zod · OpenAI
🤖 Probar el agente Repositorio SOLUCION.md

1.El problema

Hoy la analista de Compras recibe un correo con tres adjuntos y digita la orden a mano en SAP.

📥 Entrada

Solicitud (Excel), cotización del proveedor y correo de aprobación del líder.

🧮 Controles de memoria

Proveedor activo, aprobador con tope suficiente, subárea correcta, cotización vs solicitud, IVA, plazos…

⌨️ Digitación manual

Lenta, propensa a error y sin registro de las excepciones que se dejan pasar.

2.La solución

Lo determinista se hace con código; el modelo orquesta y conversa.

10controles RC1–RC10 como código puro
5herramientas tipadas con zod
13pruebas sin red ni clave de modelo
6/6casos del demo resueltos como se espera
Idea central: el modelo nunca decide un monto ni una confirmación. Los valores salen de las herramientas, y la confirmación humana se fuerza en el backend: una excepción solo se aprueba si el agente preguntó antes y el usuario respondió que sí en su mensaje siguiente.

3.Arquitectura

Comportamiento, conocimiento y ejecución, separados.

4.Ciclo del agente

  1. El usuario escribe. El backend arma el prompt con el conocimiento del proceso y el historial, y llama al modelo con las 5 herramientas.
  2. El modelo pide herramientas. Cada llamada se valida con zod, se ejecuta y queda en el historial visible del chat y en out/log.jsonl.
  3. Confirmación humana. Si hay excepciones, el agente muestra los dos valores en conflicto y pregunta. El backend solo acepta confirmado=true tras esa pregunta y un "sí" explícito del usuario.
  4. Creación idempotente. La OC se crea en SAP simulado; repetir la solicitud devuelve la misma orden, y se genera la evidencia (PDF + TXT con sha256).
  5. Topes y errores. Máximo de iteraciones por turno, tokens por sesión y globales; los errores del modelo se muestran en lenguaje claro y la sesión sigue activa.

5.Matriz de controles

CódigoControlEfecto
RC1Proveedor existe en el maestro (NIT normalizado; si no hay NIT, por nombre) y está activoBloquea
RC2Hay aprobación con "Aprobado" y quien aprueba es aprobador del centro de costoBloquea
RC3El valor no supera el tope del aprobador (sugiere quién sí lo cubre)Bloquea
RC4El centro de costo existe y la subárea le perteneceBloquea
RC5Cotización presente y dentro del 2 % de la solicitudConfirma
RC6Indicador de IVA informado; si falta se propone el default del proveedorConfirma
RC7Condiciones de pago informadas; si faltan se usa el defaultInforma
RC8La factura no es anterior a la solicitud (OC retroactiva)Confirma + marca
RC9La aprobación no es anterior a la solicitudConfirma
RC10cantidad × valor unitario = valor total, con montos positivosBloquea

Lo más difícil fue RC5/RC8: dependen de texto libre con montos en formato colombiano (11.400.000), NIT con dígito de verificación y referencias de formatos distintos. Si una factura existe pero no se entiende, el sistema falla en vez de ignorarla, porque ignorarla ocultaría una OC retroactiva.

7.Adaptador SAP real (diseño)

Integración

OData API_PURCHASEORDER_PROCESS_SRV vía Integration Suite, con deep insert atómico. Alternativa en ECC: BAPI_PO_CREATE1.

Autenticación

OAuth2 client credentials con rol mínimo; secretos en un gestor, nunca en el agente ni en el modelo.

Idempotencia

El solicitud_id viaja como referencia externa; antes de reintentar un timeout se consulta por esa referencia.

Plan B

Si no hay conexión: OC lista para pegar (ME21N) o archivo de carga masiva con el payload validado.

Pendiente con SAP: grupo de compras (obligatorio y ausente del payload), tipo de documento, cuenta de mayor y el uso de la subárea. El detalle del mapeo está en la sección 6 de SOLUCION.md.

8.Hallazgo de proceso: OC retroactivas

En sol-005 la OC se pide después de que llegó la factura, y la propia aprobación lo dice: "Ya llegó la factura, por favor crear la OC para poder radicarla". La OC está funcionando como un trámite de radicación y no como un control previo: nadie validó precio, proveedor ni presupuesto antes de comprometer.

1. Medir

El agente registra retroactiva en cada intento; control.csv permite medir la tasa y el rezago por área y proveedor.

2. Política

"Sin OC no hay pago", con una vía de excepción explícita y de nivel superior.

3. Prevenir

Acuerdos marco u OC abiertas para compras recurrentes, como la papelería trimestral.

4. Alertar

Aviso a quien aprueba cuando la factura precede a la solicitud.

10.Cómo ejecutarlo

git clone https://github.com/jogarzonpa-lang/agente-ordenes-compra-sap.git
cd agente-ordenes-compra-sap
bun install

bun run demo.ts     # 6 casos sin modelo
bun run test        # 13 pruebas sin red

export OPENAI_API_KEY=sk-...
bun run dev         # chat en http://localhost:7860

También se puede verificar en Kaggle con el notebook del repositorio, que ejecuta este mismo backend.
